# Member 2 RSA and JWKS implementation

Date: 2 November 2026 (Asia/Colombo). Branch: `Nimsara/feat/IAM-Service`.

## Implementation

- Added immutable RSA key loading under `auth-iam-service/config`. Configured keys
  must be a matching PKCS#8 private and X.509 public PEM pair with at least 2048
  bits. Key mismatch and malformed values fail startup with messages that do not
  reveal input material.
- RSA signing without configured keys is allowed only in the explicit `dev`
  profile, where IAM creates a temporary in-memory 2048-bit pair and logs a warning.
- `JWT_ALGORITHM` accepts only HS256 or RS256. HS256 remains the default and is
  selected explicitly. RS256 access tokens include a stable public-key fingerprint
  in `kid`. Verification pins the configured algorithm, key, issuer and audience,
  then checks expiry and required canonical user/session claims.
- Added unauthenticated IAM `GET /api/v1/auth/.well-known/jwks.json` returning a
  standard `{ "keys": [...] }` document with only RSA public fields and a
  `Cache-Control: public, max-age=300` header. HS256 mode with no RSA pair returns
  `{ "keys": [] }`; it never publishes the HMAC secret.
- Synchronized algorithm/key settings in `.env.example`, `.env`, Compose, local and
  AKS IAM configuration. The actual local `.env` remains byte-identical to its
  template. No gateway or other member's service code was changed.
- Updated the IAM static API contract and regenerated only its TypeScript output.

tampering, algorithm confusion, unknown/missing/copied `kid`, wrong issuer/audience,
expiry, missing claims and canonical identity; and 4 real HTTP tests using an
ephemeral development key. HTTP tests verify JWKS reconstruction, actual RS256
login, logout/session revocation, refresh replay and password-change behavior with
the existing IAM database and Redis. Their fixtures were uniquely named and cleaned.

The existing Node 22 `npm ci` flow with the unchanged lockfile passed API type
generation, frontend lint, TypeScript checks and production build. `docker compose
config --quiet` passed. The frontend build retains its existing chunk-size advisory.

## Rollout boundary

HS256 remains active by default so the existing gateway continues to accept logins.
The gateway already routes the JWKS URL, but `JwtAuthenticationGlobalFilter` does
not currently allow that path without authentication. Member 1 must permit only
`GET /api/v1/auth/.well-known/jwks.json` anonymously and implement RS256/JWKS
verification before the environment selects RS256. This work intentionally contains
no gateway changes. Key overlap/rotation, JWKS cache refresh and production unknown
key behavior require a later coordinated decision; the current provider serves one
configured key.
